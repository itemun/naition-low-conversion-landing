# Инструкция для студентов

## Порядок работы

1. Скопируйте содержимое папки `web-site/` в свой репозиторий на GitHub (в корень или в папку `web-site/`).
2. Создайте счётчик в [Яндекс.Метрике](https://metrika.yandex.ru/) и вставьте код счётчика в `index.php` перед закрывающим тегом `</body>` (на месте комментария-заглушки).
3. Включите **Вебвизор**, **Карту кликов** и **Отслеживание ссылок** в настройках счётчика.
4. Зайдите в control-panel, авторизуйтесь через GitHub, укажите ссылку на свой репозиторий и нажмите **Deploy**.
5. После деплоя запустите **Run visits simulator** (по умолчанию 100 визитов).
6. Проанализируйте данные в Яндекс.Метрике (Вебвизор, карта кликов, конверсии).
7. Получите рекомендации от AI-агента и внесите изменения в страницу.
8. Нажмите **Redeploy** (данные в БД будут сброшены) и снова запустите симулятор.
9. Сравните конверсию до и после изменений.

## Что можно менять

- Тексты, заголовки, описания
- Цвета, шрифты, отступы, визуальное оформление
- Изображения
- Расположение элементов **внутри** секций
- Видимость CTA через CSS (но не удаляйте сами кнопки)

## Что нельзя менять (сломается симулятор)

- Форма `#registration-form` с `action="api/submit.php"`
- Поля формы: `name`, `phone`, `email`, `purpose`
- Скрытое поле `bot_session_id`
- Скрипт `<script src="api/visit.php">` в `<head>`
- Классы: `.btn-register`, `.pricing-section`, `.program-module`, `.program-list`
- PHP-файлы в папке `api/` и схема `sql/schema.sql`

## Локальный запуск (опционально)

```bash
cd web-site
php -S 127.0.0.1:8765
curl http://127.0.0.1:8765/api/init.php
```

## Проверка конверсии

- Симулятор выводит свою конверсию в консоль (может отличаться от Метрики).
- Локальные данные: `https://ваш-домен/api/export.php`
- Админка заявок: `https://ваш-домен/admin/orders.php` (пароль: `FirstAid2026!`)

## Воронка регистрации (версия baseline-15.6-analytics-v1)

База: коммит `4abee11`, 500 успешных визитов симулятора, 78 заявок (15,6%),
0 ошибок, 2665,5 секунды — результат, сообщённый владельцем сайта.
Новая версия меняет только аналитику; дизайн и API сохранены.

В счётчике 113670655 настроены 10 отдельных целей типа «Целевое событие»
(бывшее «JavaScript-событие») с точным совпадением идентификаторов:

| Идентификатор | Значение |
| --- | --- |
| registration_page_view | Страница загрузилась, JS воронки запущен |
| registration_cta_view | Не менее 50% кнопки попало в экран |
| registration_cta_click | Клик по кнопке записи |
| registration_form_view | Не менее 50% первого поля формы попало в экран |
| registration_form_start | Первое изменение поля формы |
| registration_submit_view | Не менее 50% кнопки отправки попало в экран |
| registration_validation_error | Браузер заблокировал отправку: поле и категория ошибки |
| registration_submit | Началась отправка валидной формы |
| registration_submit_error | Ошибка сети, HTTP, JSON или отказ API |
| registration_success | API ответил успешно и вернул ok |

События также отправляются через `params` в ветку `landing_events`, поэтому
доступны в параметрах даже без настроенных целей. Для отчёта по конверсиям
нужно создать цели. Документация: https://yandex.ru/support/metrica/ru/objects/reachgoal

Параметры: `version`, `elapsed_seconds`, `viewport`; у кнопок — `placement`
(hero, program, pricing_1/2/3), у ошибок полей — `field` и `reason`, у ответов
API — `request_ms`. Значения полей и тексты ошибок в аналитику не передаются.
`placement` у заявки — последняя нажатая кнопка либо direct, не доказательство
причины конверсии. Видимость при прокрутке не означает прочтение элемента.
Просмотры и начало заполнения отправляются один раз на загрузку страницы;
ошибка валидации — один раз на пару поле/категория. Попытки отправки считаются все.

После публикации сначала проверить события на одном визите и их поступление
в Метрику, затем запускать пакет из 500. Сегментировать по `landing_version`
и времени запуска; исключить ручную проверку. Для воронки сравнивать визиты
с достижениями, а не число событий. Часть посетителей может попасть к форме
без клика по CTA, поэтому клик не является обязательным этапом.
Сверять итог с симулятором: блокировки Метрики и фильтрация роботов могут
уменьшить наблюдаемую выборку. Цели и параметры сами по себе не доказывают
причинность; следующий эксперимент должен менять одну гипотезу.

## Собственная карта поведения

Версия `baseline-15.6-heatmap-v1` сохраняет прежний дизайн и добавляет
независимую от Метрики телеметрию. `api/` и учебная SQL-схема не изменены.

- Сборщик: `telemetry/collect.php`, только POST, ограниченные типы событий.
- Хранилище: `/var/www/analytics-data/events.sqlite`, вне публичного каталога.
  Dockerfile создаёт каталог с владельцем www-data. Для локальных проверок
  путь задаётся через `ANALYTICS_DATA_DIR`.
- Отчёт: `/admin/analytics.php`. Вход через существующую админку
  `/admin/orders.php`; применяется та же сессия, отдельного публичного экспорта нет.
- Выгрузка: кнопка «Скачать данные перед Redeploy». Сохраняйте JSON до деплоя:
  каталог с аналитикой не является постоянным томом и может быть удалён.
- Ручные проверки: открывайте сайт с `?analytics_qa=1`. Такие загрузки
  по умолчанию исключены из собственного отчёта (на Метрику флаг не влияет).
- Встраивание страницы картой Метрики с `_ym_debug` отключает собственный сбор.

Данные: случайный ID на загрузку, версия, класс ширины экрана, время первого
получения сервером в UTC, порядковые номера и время действий от загрузки.
Клики привязаны к фиксированным именам элементов и нормированы внутри их
границ. Клавиатурные клики учитываются без координат. Значения полей,
тексты страницы, URL, IP, user-agent и постоянные идентификаторы сборщик
в SQLite не сохраняет. Стандартные логи веб-сервера и ранее подключённая
Метрика работают отдельно.

Видимость секций измеряется примерно раз в секунду только в активной вкладке.
Накопленное время отправляется пакетами раз в четыре секунды и при скрытии
страницы. Это приблизительное время на экране, не время чтения. Поля
отслеживаются по фокусу, начало ввода и успех — по событиям основной формы.
Повторная доставка дедуплицируется по ID загрузки и номеру события.
Лимиты: до 3000 событий на загрузку, 100 в пакете, очередь до 500 событий.
При закрытии вкладки или сбоях сети часть данных может потеряться.

Для анализа выберите период запуска в UTC, версию и при необходимости класс
экрана. Сначала сравните количество загрузок и подтверждений API с симулятором,
затем изучите видимость секций, клики и отдельные последовательности действий.
Группа «Без подтверждённой заявки» может содержать визиты с потерянным событием
успеха. Карты сравниваются внутри конкретного элемента, а не накладываются на
скриншот другой ширины. Это наблюдательные данные; причину роста проверяет A/B.

Проверка сборщика на отдельном локальном сервере: `python3 tests/telemetry_http.py`.
Скрипт разрешает только адрес 127.0.0.1 и создаёт тестовую запись с qa=true.
